# 模型智力检测 · 设计文档

> 状态：已确认需求，待编码。UI 采用 [方案 A · 状态页式](./UI方案A-状态页式.html)。

## 1. 背景与目标

对承诺「不降智」的分组做定时能力检测：每个周期用与 Codex CLI 一致的请求方式，向每个受检分组发送一道逻辑题和一道绘图题，记录每次结果，并在一个**无需登录**的公开页面上以色块时间线展示，让用户自行验证"模型是否满血在跑"。

## 2. 已确认的决策

| 事项 | 决策 |
|------|------|
| 用户端 UI | 方案 A（状态页式）：每组一张大卡，左侧两条 48 格时间线，右侧最新画作，点击色块弹出详情 |
| 访问权限 | 公开路由，未登录可看；受管理端 `enabled` 开关控制（关闭时前端重定向、后端 404） |
| 详情弹窗信息 | 展示题目、期望答案、提取答案、模型原始回复、耗时、推理等级；**不展示上游 URL、API Key、HTTP 细节** |
| 逻辑题判定 | 精确 / 数值 / 包含 / 正则四种匹配模式，管理端选择 |
| 绘图题判定 | **两层必过**：① 相对参考稿的结构门禁（各指标 ≥ 参考稿的 70%，可配）；② 源码评审——由管理端指定的评审模型读 HTML 源码按清单打分，≥ 80 分通过（可配）。不做视觉截图评审。标定样例：`海风骑行`（参考）、`晴日骑行` 应通过；`2D_SVG_独立版`、`SVG动画` 应失败 |
| 题库 | 逻辑题、绘图题各 1 道（表结构支持多题，运行时按 `enabled` 抽取，只有 1 道时即固定） |
| 降智判定 | `degraded_rule` 可配置：连续 N 次逻辑题失败 → 疑似降智；连续 M 次通过 → 恢复正常；请求失败不计入连续计数 |
| 调度 | `time.Ticker` 按 `interval_minutes` 定时 + `LeaderLockCache` 单实例执行（**不用 cron**，理由见 §4.2） |

## 3. 数据模型

### 3.1 新表（手写 SQL 迁移 `backend/migrations/NNN_intel_check.sql`，ent schema 同步）

```
intel_check_targets            受检分组
  id, name(100), description(500), base_url(500), api_key_encrypted(text, AES-256-GCM),
  api_mode(responses|chat_completions), model(200), reasoning_effort(low|medium|high|xhigh),
  rate_label(20, 展示用倍率文案如 ×0.3), enabled bool, sort_order int,
  created_by, created_at, updated_at
  索引: (enabled, sort_order)

intel_check_questions          题库
  id, kind(logic|drawing), title(100), prompt(text),
  expected_answer(500, 逻辑题用), match_mode(exact|numeric|contains|regex),
  reference_html text(绘图题参考稿原文), reference_metrics jsonb(上传参考稿时服务端自动计算, 见 §5.2),
  drawing_rules jsonb(绘图题门禁配置, 见 §5.2), review_rubric text(源码评审清单, 有默认模板),
  enabled bool, created_at, updated_at
  索引: (kind, enabled)

intel_check_rounds             轮次
  id, seq bigint unique(展示用 #1284), started_at, finished_at nullable,
  logic_question_id, drawing_question_id (FK questions, ON DELETE SET NULL),
  trigger_source(cron|manual)

intel_check_results            明细（每轮 × 每组 × 每题一行）
  id, round_id FK cascade, target_id FK cascade, kind(logic|drawing),
  status(pass|fail|request_error|running), latency_ms int nullable,
  prompt_snapshot text(本轮实际发送的题面), raw_reply text, extracted_answer(500),
  html_output text(原样保留的 HTML, 仅绘图题), judge_detail jsonb(逐项规则结果),
  error_message(500), input_tokens int, output_tokens int, checked_at timestamptz
  索引: (target_id, kind, checked_at), (round_id), (checked_at),
        (round_id, target_id, kind) UNIQUE
```

几处与直觉不同、编码时确定下来的约定：

- **`trigger` 必须命名为 `trigger_source`**：`TRIGGER` 是 Postgres 保留字。
- **`trigger_source` 的取值保留 `cron` 字面量**，尽管 §4.2 已改用 ticker 调度。这里读作「自动定时触发」，与 `manual` 相对。不改名是因为该值写在迁移的 CHECK 约束里，迁移文件一旦落库就受 SHA256 校验保护、不可编辑；为一个语义等价的标签再加一次迁移不划算。
- **`rounds` 与 `results` 不带 `created_at`/`updated_at`**：二者已分别以 `started_at`、`checked_at` 作为时间锚点，再加一个创建时间会让清理任务和查询产生歧义。`targets` 与 `questions` 是配置表，沿用 TimeMixin。
- **全部四张表都不带 `deleted_at`**：迁移 127 已明确把软删除从日志类表上摘掉，明细表没有恢复需求，软删除只会让行数与索引单调膨胀。
- **`(round_id, target_id, kind)` 唯一索引是正确性基础**：本方案先插 `running` 行再原地更新为最终结果，缺了这个约束，一次重试就会让时间线凭空多出一个色块。
- 时间线主索引不需要单独建 DESC 版本，Postgres 可反向扫描；独立的 `(checked_at)` 索引供留存清理使用。
- **`rounds.seq` 由独立序列发号（迁移 `239_add_intel_check_round_seq.sql`）**。238 号迁移把它建成普通 `BIGINT NOT NULL` + 唯一索引，取值方式留给应用层，但 `MAX(seq)+1` 站不住：保留期清理会物理删除过期轮次，服务停机超过 `retention_days` 把表清空后，轮次号会从 #1 重新开始，与「清理旧数据后不回退」的承诺矛盾；且 leader lock 若因续约失败被两个实例同时持有，`MAX+1` 会直接撞唯一索引。序列的取值不受表内现存行影响，`nextval` 本身也并发安全。不改 238 而另起一条迁移，是因为迁移文件落库后受 SHA256 校验保护。

### 4.1 分层与文件

```

  intel_check_repository.go       仓储接口 + 哨兵错误

  intel_check_settings.go         设置校验（纯函数）
  intel_check_service.go          服务壳 + 设置读写 + key 加解密
  intel_check_target_service.go   受检分组 CRUD（含入参校验）
  intel_check_question_service.go 题库 CRUD
  intel_check_public_service.go   公开视图聚合（概览 + 单次详情，出口处只搬运允许公开的字段）
  intel_check_runner.go       ticker 调度 + leader lock + 单轮执行编排（pond 池并发）
  intel_check_logic.go        逻辑题：组请求 → 提取答案 → 匹配
  intel_check_drawing.go      绘图题：从回复中抽取 HTML/SVG（**不改写产物**，理由见 §7）
  intel_check_gate.go         第一层结构门禁：比例项 + 固定项判定（从 drawing 拆出，控制在 300 行内）
  intel_check_metrics.go      结构指标计算（参考稿与候选稿共用，纯函数）
  intel_check_review.go       源码评审：组提示词 → 调评审模型 → 解析 JSON 评分
  intel_check_status.go       degraded_rule 推导「智力正常 / 疑似降智」
internal/repository/intel_check_repo.go
internal/handler/intel_check_handler.go          公开接口
internal/handler/admin/intel_check_handler.go    管理接口
```

每个文件 ≤ 300 行，配套 `_test.go`，沿用 `channel_monitor_*_test.go` 的 stub 风格。

三处编码时确定的约定：

- **哨兵错误用 `infraerrors.NotFound(REASON, 中文文案)` 这类语义化构造函数**（定义在 `internal/pkg/errors/types.go`，与 `setting_service.go` 等既有服务一致），状态码由构造函数决定，handler 用 `infraerrors.Code(err)` 取出，不必再维护一张错误到状态码的映射表。另有两点值得记下：`ApplicationError.Is` 按 `Code + Reason` 判等而非指针相等，所以经 `WithCause`/`Clone` 包装后 `errors.Is` 依然命中；`ErrIntelCheckDisabled` 刻意取 404 而非 403——403 等于承认「有这个功能但不给你看」，而开关关闭时不应让外部探知其存在。
- **设置的归一化与校验分工明确**：数值越界由 `NormalizeIntelCheckSettings` 静默收敛（`interval=2000` → 1440 比报错更有用），`ValidateIntelCheckSettings` 只拦收敛不了的问题（文案超长、`enabled=true` 但评审模型未配）。写路径先归一化再校验，顺序颠倒会让可自动修正的输入变成报错。归一化对 `Enabled` 不做任何回落——bool 零值就是 false，若套用「零值回落默认」，管理员关掉的开关会在下一次读取时自己打开。
- **公开页的响应体另有一套结构体（`IntelCheckPublic*`），不复用领域模型**。`IntelCheckTarget` 带 `BaseURL`/`APIKey`、`IntelCheckResult` 带 `ErrorMessage`，只要哪天有人图省事把领域模型直接序列化出去，上游地址与凭据就随之泄露；字段逐个列出后，漏字段只是少显示一项，加错字段才是事故。聚合逻辑因此也从 `intel_check_question_service.go`（已 268 行）挪到独立文件，避免为塞进 300 行上限而把公开出口拆散在两处。

### 4.2 调度方式：`time.Ticker` 而非 cron

最初设想复用 `OpsCleanupService` 的 `*/N * * * *` cron 表达式，编码时发现**这条路在本功能的配置区间内是错的**：

- `interval_minutes` 的合法区间是 5–1440 分钟，而 cron 分钟位的 `*/N` 只在 N ≤ 59 时合法。管理员填 90 或 120，表达式直接解析失败。
- 即便 N ≤ 59，只要不能整除 60 就会失真：`*/45` 实际是「每小时的第 0、45 分钟」，间隔在 45 与 15 之间交替，与「每 45 分钟检测一次」的字面承诺不符。

cron 的语义是「在某些时刻」，而这里要的是「每隔多久」，两者只在 N 整除 60 时恰好重合。因此改用 `time.Ticker`：

- 周期直接取 `time.Duration(interval_minutes) * time.Minute`，与配置项一一对应，不存在失真区间。
- 多实例互斥仍由 leader lock 保证，改用较新服务采用的 `service.LeaderLockCache` 抽象，而非 `ops_cleanup_service.go` 里内联的 SetNX + Lua。
- 沿用 `mu + started/stopped + Reload()` 的生命周期写法：管理端改了 `interval_minutes` 后调 `Reload()` 重建 ticker，`Stop()` 需挂进 `cmd/server/wire_gen.go` 中 `provideCleanup` 的 `parallelSteps`。

**已知取舍**：ticker 的相位随进程启动时刻漂移，重启后不保证落在整点。本功能只承诺「每隔 N 分钟检测一次」，不承诺检测时刻，故可接受；若日后要求整点对齐，再在首次触发前补一次对齐等待即可，不影响其余设计。

### 4.3 单轮执行流程

1. ticker 触发 → 抢 leader lock → 读设置，`enabled=false` 直接返回。
2. 抽取 enabled 的逻辑题、绘图题各 1 道，创建 `round`。
3. 对每个 enabled target：先各写一行 `status=running` 的 result（前端"检测中"浅蓝块），再投入 pond 池。
4. 逻辑题：按 `api_mode` 组流式请求体（responses 模式带 `reasoning.effort`，`stream=true`），复用 `newSSRFSafeHTTPClient`；按事件增量消费 SSE（不缓存完整传输体，2 MiB 上限只约束最终文本，单个事件上限 16 MiB）并收到协议终止事件后提取答案，再按 `match_mode` 判 `pass/fail`；网络错误 / 非 2xx / 超时 / 流未完整结束 → `request_error`，不得用半截回复判题。
5. 绘图题：受检模型作答同样使用流式请求，完整收流后从回复中抽取 ```html 代码块或 `<html>…</html>`；**产物原样保留、只查体积上限**（不做任何改写，理由见 §7）→ 结构门禁（§5.2 第一层）→ 门禁通过后再调评审模型做源码评审（第二层，短 JSON，继续使用同步非流式请求）→ 两层皆过才 `pass`；逐项结果与评审理由存 `judge_detail`。源码评审可由 `drawing_judge.skip_review` 关闭，关闭时在门禁判定后直接短路，不产生任何评审侧请求（见 §5.2）。
6. 更新 result，全部完成后写 `round.finished_at`。
7. 每日维护挂入 `OpsCleanupService`，按 `retention_days` 清理 results/rounds。
8. 管理端「立即跑一轮」调用同一执行函数（`trigger_source=manual`），不经 ticker 但同样抢锁。

### 4.4 降智判定（`intel_check_status.go`）

取该 target 最近 `timeline_points` 条逻辑题结果，按时间倒序：忽略 `request_error/running`，统计连续 `fail` 与连续 `pass`。状态机：

- 当前为「正常」且连续 fail ≥ `fail_streak` → 「疑似降智」
- 当前为「疑似降智」且连续 pass ≥ `recover_streak` → 「正常」
- 无有效数据 → 「暂无数据」

纯函数，便于单测覆盖各边界。

**状态由历史回放得出，不落库**（`ReplayIntelCheckState`）。滞回依赖「上一次判定的状态」，而表里没有这一列：拿全量历史只调一次 `DeriveIntelCheckState`、`previous` 恒传空，「连续 M 次通过才恢复」就失效了——某组连续 3 次失败已判降智、其后只通过 1 次时，单次调用看到 `leading=pass`、`streak=1`，不满足降智条件便直接返回「正常」，而 `recover_streak=2` 要求它仍是「疑似降智」。因此从最旧一条起逐条推进状态机。不为它加一列，也就不会出现「存储的状态与历史对不上」这类只能靠重算修复的脏数据；`timeline_points` 条的回放是内存中的线性扫描，成本可忽略。

绘图题不参与状态判定：它的判定含源码评审打分，天然比逻辑题波动大，纳入会频繁误报。

### 4.5 接口

公开（`/api/v1/public/intel-check`，不挂 JWT，`enabled=false` 返回 404）：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/overview` | 页面文案、汇总（正常/降智数、24h 通过率、下次检测时间）、每组卡片数据（两条时间线、统计、最新画作 result_id） |
| GET | `/results/:id` | 单次详情：题目快照、期望/提取答案、原始回复、耗时、推理等级；绘图题额外返回 `html_output` 与 `judge_detail`。**不含 base_url / api_key / HTTP 状态码** |

三点编码时定下的口径：

- **统计窗口固定 24 小时，不由 `timeline_points` 反推**。48 格只在 `interval=30` 分钟时恰好等于 24 小时；管理员改成 5 分钟后同样的 48 格只覆盖 4 小时，而页面文案仍写着 24 小时。
- **`next_check_at` 锚在上一轮的开始时刻**而非结束时刻——结束时刻随上游耗时波动，用它推算会逐轮漂移。它是预计值不是承诺；该时刻已过去也照实返回，不做美化：那恰好说明调度停了，藏起来只会让故障更难发现。一轮都没跑过时留 `null`，让前端显示「尚未开始检测」，塞当前时间会让页面看起来刚检测过。
- **错误原文一律换成按状态生成的中性文案 `status_note`**。`error_message` 可能带上游域名、状态码乃至凭据片段，这是「不展示上游细节」这条承诺在后端唯一的落点；连带约束 runner：请求类失败写 `error_message`（不对外），`judge_detail` 会原样公开，不得把上游报错塞进去。

### 4.6 运行期取舍与已知限制

编码 runner 时定下的四条口径，都会直接影响公开页上色块的含义：

- **评审模型自己挂了记 `request_error`（黄），不算受检模型失败。** 责任方不同：评审侧抖动若落成红块，等于用检测链路的故障去指控被检对象降智，而这张页面的全部价值就在于指控必须准确。
- **并发粒度是「分组」，同组的逻辑题与绘图题串行。** 两题共用同一把上游凭据，并行发只会给自己制造限流，而限流会被记成 `request_error`——那是用检测行为污染检测结论。
- **`xhigh` 等推理等级原样透传，不做静默降级。** 本功能要证明的正是「跑的是满血配置」，在客户端悄悄降到 `high`，结论就自我否定了。上游不支持该取值会回 400，落为 `request_error`，不计到模型头上。
- **轮次有硬上限**（一个检测周期，下限保底为「单次请求超时 + 1 分钟」）。跑过头的轮次会与下一轮抢同一批分组的配额，与其让两轮互相拖慢，不如截断；未完成的分组落成黄块，那本就是需要被看见的信号。锁 TTL 取该上限再加 2 分钟，确保它不会在轮次执行中途过期。

两个已知限制，均为有意接受而非遗漏：

- **进程崩溃会遗留 `running` 行**（公开页上表现为一直不褪色的浅蓝块）。不做启动扫描修复：那需要为一个极低频场景新增仓储方法与启动期全表扫描，而多实例部署下「另一实例正在跑的 running」与「崩溃遗留的 running」无法仅凭数据库状态区分，误清会把在跑的轮次抹成失败。留待保留期清理自然回收。
- **轮次号（`seq`）会出现空洞**。发号在事务内取 `nextval`，插入回滚时号已消耗。空洞无害：`seq` 只用于展示「第 #1284 轮」，连续性不承载任何语义。

## 5. 判定规则

### 5.1 逻辑题答案提取

1. 优先取最后一个有效的 `\\boxed{...}` / `\\fbox{...}` 最终结论（支持 `\\boxed{21\\text{颗}}` 这类嵌套 LaTeX），再依次尝试「答案是 X」句式、最后一个 `**…**` 加粗片段、最后一行；
2. `numeric` 模式：提取首个数字与期望值做数值比较（允许 `21` / `21.0`）；
3. `exact`：去首尾空白与标点后全等；`contains`：包含即通过；`regex`：管理端填正则。

### 5.2 绘图题判定（两层必过）

#### 第一层：相对参考稿的结构门禁

上传参考稿时服务端计算 `reference_metrics`，候选稿计算同一组指标，**每项都须 ≥ 参考值 × `min_ratio`**（默认 0.7，`drawing_rules.min_ratio` 可配）：

下表为 4 份标定样例的**实测值**（`TestIntelCheckDrawingCalibration` 输出，括号内为占参考稿的比例）：

| 指标 | 计算方式 | 参考稿① | ③ 应过 | ② 应挂 | ④ 应挂 |
|------|---------|--------|-------|-------|-------|
| `shape_count` | `path/circle/ellipse/rect/line/polygon/polyline/use/text` 元素数 | 116 | 97 (84%) | 63 (54%) ✗ | 46 (40%) ✗ |
| `animated_targets` | SMIL 元素的父节点数 + CSS `@keyframes` 被 class 引用的元素数 + JS 中 `getElementById/querySelector` 命中的被 `setAttribute/transform` 驱动的 id 数 | 23 | 19 (83%) | 13 (57%) ✗ | 15 (65%) ✗ |
| `defs_symbols` | `<defs>` 内 `g[id]/symbol/pattern/gradient/filter` 数 | 7 | 7 (100%) | 6 (86%) | 3 (43%) ✗ |
| `path_data_bytes` | 所有 `d` 属性总字节数（造型精细度代理） | 3100 | 2789 (90%) | 1709 (55%) ✗ | 1298 (42%) ✗ |
| `html_bytes` | 产物 HTML 大小 | 19627 | 17380 (89%) | 9994 (51%) ✗ | 10104 (51%) ✗ |

固定项（不随参考稿变化）：存在 `<svg>` 且可解析；同时存在 `<title>` 与 `<desc>`（或 `aria-labelledby` 指向二者）；命中 `required_keywords`；≥ 1 种动画机制（SMIL / `@keyframes` / `requestAnimationFrame|setInterval|animate(`）；`html_bytes ≤ max_bytes`。样例 ④ 额外在「同时存在 title 与 desc」这一固定项上失败。

两点实测得出的注意事项：

- **`defs_symbols` 是弱判别项**：② 在该项拿到 86%，高于 ③ 的最低项 83%，单独看会把好坏样例判反。它只对 ④（43%）有效，因此不可对其加权，也不能单独用它做判定。
- **不可指定具体动画机制**：三份样例分别使用 `script`（参考稿①）、`smil`（③）、`css`（④），满血产出并不收敛到某一种机制。门禁只能要求「至少存在一种」。

```json
{ "min_ratio": 0.7, "required_keywords": ["鹈鹕", "自行车"], "max_bytes": 262144 }
```

#### 第二层：源码评审（评审模型读代码，不渲染）

门禁通过后，把原样保留的 HTML 源码 + 参考稿源码 + `review_rubric` 发给 `drawing_judge` 指定的模型，要求返回 JSON：

```json
{ "score": 0, "summary": "一句话总评",
  "items": [{ "item": "检查项名称", "score": 0, "max_score": 25, "comment": "扣分理由" }] }
```

`score ≥ pass_score` 才通过。参考稿一并送入并明示为 **90 分基准**——缺少「满血产出长什么样」的标尺，模型对孤立样本的打分会随机漂移，无法稳定区分满血与降智；参考稿为空时降级为绝对打分并在提示词中说明，避免模型自行脑补标尺。

清单分两级：

**内置默认清单**（题目未配置 `review_rubric` 时使用，必须与具体题目无关）。按「降智时最先丢失的能力」排序——降智模型通常先丢细节与动画联动，最后才丢整体构图：

1. 主体完整度（25 分）：题面要求的主体是否齐全，各部件是否分离建模；
2. 结构合理度（20 分）：部件比例、连接关系、遮挡层次是否正确；
3. 动画质量（25 分）：是否持续动画，多部件是否联动（而非整体平移），运动是否符合物理直觉；
4. 细节丰富度（20 分）：背景、光影、渐变、点缀元素是否到位；
5. 代码工程性（10 分）：是否使用 defs/symbol 复用、有无 title/desc、结构是否清晰。

**题目级清单**（存 `questions.review_rubric`，覆盖内置清单）。鹈鹕骑自行车这道题应录入以下 7 条，它们依赖该题特有的部件语义，不可作为内置默认值：

1. 主体朝向与行进方向一致（车把/前轮所在侧 = 头/喙所在侧）；
2. 车轮旋转中心位于轮心（SMIL `rotate cx cy` 或 CSS `transform-origin` 落在圆心；无"多个轮子共用一个 g 旋转"）；
3. 曲柄旋转中心位于车架下管交点（不是鞍座/车把）；
4. 脚部始终跟随踏板（腿部有随曲柄相位变化的动画，非静态曲线）；
5. 无重叠冗余（如静态辐条与旋转辐条同时存在）；
6. 场景元素 ≥ 3 类背景道具（云/浪/船/灯塔/花草等）且有独立动画；
7. 主体细节完整（喉囊、长喙、眼睛、围巾等题目要求的特征）。

样例 ② 触发第 3、4、5 条（曲柄绕鞍座顶点 (530,466) 转、脚与踏板脱节、`#wheel` 内静态辐条与旋转辐条重叠）；样例 ④ 触发第 1、2、4 条。这两份样例在第一层门禁就已被拦下，此处仅作为清单条目的语义示例。

#### 默认阈值的来源

`min_ratio = 0.7` 由上表实测数据推导，不是拍脑袋取的整数。

门禁的判定是「任一项不达标即失败」，所以阈值的可用范围由两端夹出来：

- 要让 ③ 通过，阈值必须 ≤ 它的**最低项** 83%（`animated_targets`）；
- 要让 ② 被拦，阈值必须 > 它的最低项 51%（`html_bytes`）；④ 同理 > 40%。

即可用区间为 **(51%, 83%]**，0.7 接近该区间中点：向上给满血产出留 13 个百分点的正常波动空间，向下给劣质产出留 19 个百分点的拒绝余量，两侧大致对称。

**不要为了「更严格」把阈值提到 0.8**：②④ 本就各有 4 项、5 项不达标，收紧阈值不会改变它们的判定结果，却会把 ③ 的容错从 13 个百分点压到 3 个百分点——下次某份满血稿在 `animated_targets` 上正常波动到 78% 就会被自己的门禁误杀。严格应当体现在判定结果正确，而非阈值数字更大。

实测还表明：**第一层结构门禁已能独立完成 ①③ 过、②④ 挂的判定**，第二层源码评审不是本组样例的兜底手段，而是用于拦截「结构指标凑够了但实际粗糙」这类第一层看不出的退化。

**因此源码评审可关闭**（设置项 `drawing_judge.skip_review`，管理端「设置」页签上表现为「源码评审」开关）。关闭后绘图题只走结构门禁：无需配置评审分组与模型（`ValidateIntelCheckSettings` 同口径放行），每轮省下一次评审调用（绘图题本身已要一两分钟），且评审侧的抖动再也不会把受检分组染成黄块。代价是放过上面那类退化。

两处实现细节：
- 字段取负向命名 `skip_review` 而非 `review_enabled`，为的是让 JSON 零值等于既有行为——存量设置里没有这个字段时反序列化得 `false`，即「照旧评审」。若用正向命名，零值 `false` 会让所有存量部署升级后静默关掉评审，而 `Normalize` 无法区分「字段缺失」与「管理员显式关闭」（同 `Enabled` 不参与零值回落的理由）。界面上仍按正向表述，由前端取反。
- 关闭时在 `judgeIntelCheckDrawing` 内就短路返回，并跳过 `loadIntelCheckJudgeTarget`，确保「关闭」真的意味着不产生任何评审侧请求与失败面，而不是把 `nil` review 交给下游判定。

### 5.3 门禁与评审的分工边界

门禁只能数**数量**（造型数、动画目标数、路径字节数、体积），数不出**结构正确性**。实测中反复出现的一类缺陷正好落在这条缝里：车轮的旋转中心没落在轮心，看起来是「轮胎飞了」。两种写法都会触发它——

- SMIL：`<animateTransform type="rotate">` 加了 `additive="sum"`，叠加到基础值 `translate(x y)` 上，而 `rotate` 不带圆心参数时绕的是当前坐标系原点；
- CSS：同一元素上既有 SVG `transform` 属性又有 CSS transform 动画，后者优先级更高，动画一跑 `translate` 就被整个替换掉。

正确写法是拆成两层 `<g>`：外层只 `translate` 定位，内层只 `rotate`。

这类缺陷**必须由源码评审判定**（题目级清单第 2 条），门禁无论怎么加阈值都抓不到。因此关闭评审时应当知道：绘图题退化为「画得够不够多」的检测，画得对不对不再被考核。

样例作为 Go 单测夹具放在 `backend/internal/service/testdata/intel_check/`，由 `TestIntelCheckDrawingCalibration` 对三份样例的判定结果逐一断言。阈值变更必须同时让 4 份样例保持预期结果——健康样例被拦下说明过严，劣质样例被放行说明过松，两个方向都会让该用例失败。

## 6. 前端设计

### 6.1 路由与守卫

- `/portal/intel-check`，`requiresAuth:false`，参照 `/model-plaza` 守卫：仅在设置**已成功加载且明确为 `false`** 时重定向（瞬时加载失败是未知状态而非确认关闭，交给后端 404 兜底，避免网络抖一下就把页面判成「功能没开」）。
  - 挂在 `/portal` 下而非顶层 `/intel-check`：它与可用性检测、定价方案同属对外公示页；且 `BACKEND_MODE_ALLOWED_PATHS` 已按 `'/portal'` 前缀放行，纯后台模式下匿名可见这一点不需要再维护一条白名单。
  - 不设「强制登录」那一档（模型广场有 `require_auth`，本页刻意没有）：这张页面的用途就是让未登录者自行核验模型没被降智，要求登录等于把证据锁在门后。
- `public_settings` 新增 `intel_check_enabled` 字段；管理端菜单项受同一开关控制。
- 管理端 `/admin/intel-check`：概览 / 受检分组 / 题库 / 设置 四个页签。

`intel_check_enabled` **不新增独立设置行**，而是从 `intel_check_settings` 那一整块 JSON 里只取 `enabled`（`intelCheckEnabledFromRaw`，用一个只有一个字段的窄结构体解析）。存两份会立刻变成两个可以互相矛盾的真相来源；用窄结构体而非整块反序列化，是因为 `IntelCheckSettings` 带着评审模型名与上游分组 id，整块解进来日后很容易顺手多带一两个字段进公开响应。解析失败一律按未开启处理（fail-closed），与 `IntelCheckService.IsEnabled` 同一取舍。

后端共六处落点，缺一处就会出现「接口有、页面没有」或「刷新时菜单闪烁」：`GetPublicSettings` 的 key 白名单 → `service.PublicSettings` 定义 → 其填充 → `PublicSettingsInjectionPayload` 定义 → `GetPublicSettingsForInjection` 填充 → `dto.PublicSettings` 定义与 handler 映射。前四处由 `TestPublicSettingsInjectionPayload_SchemaDoesNotDrift` 自动兜底（它 diff 两个结构体的 JSON tag 集合），漏了会直接失败。

管理端路由**刻意不挂功能开关守卫**（不同于 `registerChannelMonitorRoutes`）：配置受检分组、录题、标定阈值全都发生在开启之前，而 `ValidateIntelCheckSettings` 又要求开启前必须已配好评审模型——用开关守卫这些页面会形成「想开启必须先开启」的死锁。

### 6.2 组件（`frontend/src/views/public/components/`）

放在 `views/public/components/` 而非 `features/intel-check/`：门户页的组件（`PortalLayout`、`PortalMonitorDetailDialog`、`HomePricingSection`）都在这里，而 `features/` 下的两个目录都是管理端功能模块。跟随就近的那个惯例。

| 文件 | 职责 |
|------|------|
| `IntelCheckGroupCard.vue` | 单组大卡（名称、chips、状态 pill、两条时间线、最新画作） |
| `IntelCheckTimeline.vue` | 48 格色块（pass 绿 / fail 红 / request_error 黄 / running 浅蓝脉冲 / 无数据灰），点击 emit |
| `IntelCheckResultDialog.vue` | 详情弹窗：逻辑题左右两栏；绘图题为「预览 / 源码 / 原始回复」页签 |
| `SvgArtworkPreview.vue` | `<iframe sandbox="allow-scripts" srcdoc>`：**不给** `allow-same-origin`/`allow-top-navigation`，脚本可运行（参考稿动画依赖 JS）但拿不到父页面、cookie 与网络能力；产物不经服务端改写，sandbox 是唯一防护层 |
| `intelCheckFormat.ts` | 时间/耗时/百分比格式化 |

页面 `views/public/IntelCheckView.vue` 组装以上组件，30 秒轮询 `/overview`。顶部说明卡与图例直接写在页面里，没有拆成 `IntelCheckHero.vue` / `IntelCheckLegend.vue`：两者各约 15 行标记、无处复用，拆出去只是增加一层跳转。

**样式以 [`UI方案A-状态页式.html`](./UI方案A-状态页式.html) 为准**：白卡片、24px 圆角、青绿（teal）点缀、右侧 52px 大 KPI 数字。

页面**自带样式（`ic-*` 前缀）、不使用门户的 `lc-*` 类**。这一条是踩过坑才定下来的：`lc-*` 定义在 `styles/portal-neon.css`，是一套**深色霓虹**皮肤（`.lc-card` 背景为 `rgba(19,19,22,.94)`），且文字色挂在 `.lc-shell` 上。早期版本图省事借用了它，结果有两个后果——① 页面在门户里是深色霓虹风，跟方案A的浅色设计完全不是一回事；② 一旦嵌进后台（`AppLayout` 里没有 `.lc-shell`），卡片是深色、文字色却继承自后台浅色主题，整页白字压深底、什么都看不见。

自带样式后，配色用定义在 `.ic-root` 上的 CSS 变量表达，并在 `.lc-shell .ic-root` 下整体替换为深色版：后台里是原汁原味的方案A，门户里是同一套布局的深色版，**布局、信息结构、大数字、时间轴完全一致**。

由此得出一条通用约束：**凡是自定义背景色的块，必须在同一处把文字色也定死**。只设背景、让文字色向上继承的写法，在浅色环境下测不出问题，一换主题就瞎（详情弹窗的 `.lc-ic-pre` 就这么翻过一次车）。

用户端侧边栏的入口挂 `/portal/intel-check?embedded=1`，页面据此在 `AppLayout` 与 `PortalLayout` 之间二选一（与 `ModelPlazaView` 同一模式）。未登录时即便带了 `embedded=1` 也降级为门户形态，否则转发出去的链接会渲染出一个没有登录态的空后台骨架。

四处实现口径，前三条都是从「同题同刻横向对比」这条唯一说服力来源推出来的：

- **顶部大 KPI 只统计逻辑题**。绘图题的判定含源码评审打分，天然比逻辑题波动大（后端也正因此不让它参与降智判定）。把它混进这个最显眼的数字里，会让「评审模型今天抽了一下」看起来像「模型降智了」。分子分母先各自累加再相除——逐组求平均会让样本少的分组被放大。

- **时间线补齐时空位填在左侧（较旧的一端）**。各分组历史长短不一，若都从左边开始画，最右一格就不再是同一时刻，横向对比即失效。
- **详情弹窗打开时暂停轮询**。不是为了省流量：概览重渲染会打断正在播放的画作动画，而读者点开详情多半正是为了看动画。
- **卡片上的最新画作按 result_id 去重**。`latest_drawing_result_id` 往往几十分钟才变一次，不去重则每 30 秒把几百 KB 的产物 × 分组数重新拉一遍。

### 6.3 API 与文案

`api/intelCheck.ts`（公开）、`api/admin/intelCheck.ts`（管理），类型与函数导出风格同 `api/modelPlaza.ts`。公开侧的类型里刻意没有 `base_url`/`api_key`/HTTP 状态码的位置——后端公开视图本就不返回它们，前端类型也不该给它们留空位。

**文案硬编码简体中文，不建 `intelCheck.*` 语言包**：门户页全族（`PortalStatusView` 等）都是硬编码中文，`PortalMonitorDetailDialog` 用 `t()` 是因为它复用了登录端已有的 `channelStatus.*` 键，而本功能没有可复用的命名空间。新建一套的结果会是「中文页面套一个英文弹窗」，比统一中文更糟。日后若门户整体接入 i18n，本功能随之迁移。

## 7. 安全

- API Key 仅密文入库，公开接口永不返回 target 的 `base_url/api_key`；管理接口返回脱敏 key。
- 上游请求复用 `safeDialContext`（dial 时二次校验解析出的 IP，可拦 DNS rebinding），但**不复用 `monitorHTTPClient` 实例**：后者 `ResponseHeaderTimeout=30s`、响应上限 64 KB，而本功能刻意用高推理等级、绘图产物动辄几百 KB，套用监控那档参数会把满血模型判成请求失败，恰与本功能要证明的事情相反。专用 client 把两项超时都留空，统一由 context 控制，管理员改超时即刻生效。
- `base_url` 用 `validateIntelCheckBaseURL` 而非 `validateEndpoint`：后者强制 https 并抛 `ErrChannelMonitor*` 系列错误，而受检分组允许内网 http 地址。
- 模型产出的 HTML **只靠一层隔离：`<iframe sandbox="allow-scripts">` 且不给 `allow-same-origin`**，产物运行在不透明源里——拿不到父页面 DOM、cookie、storage，也不能做顶层导航或弹窗。

  原设计是「服务端清洗 + 注入 CSP meta + sandbox」三重隔离，**上线后撤掉了前两层**，原因是它们破坏了本功能唯一要做的事：
  - 清洗用 HTML 解析器往返处理 SVG，可能改写自闭合写法与属性大小写（`viewBox`/`attributeName`/`repeatCount` 这些 SVG 必须保留驼峰），**动画因此失效，且不报任何错**；
  - 脚本按关键词整段剔除的规则尤其粗暴：动画代码里出现一个名为 `location` 的局部变量，整段动画就消失，表现出来却只是「这个模型画不出动画」；
  - 更根本的是，这张页面的全部价值在于「如实展示模型画出了什么」。任何改写都让展示物 ≠ 产出物，而门禁数的是改写后的指标、评审读的是改写后的源码、用户看到的是改写后的动画——三者一起偏离，没有任何一环会报错。

  沙箱本就是三层里唯一真正起作用的那层，清洗属于锦上添花，而它的代价是让本功能失去可信度。**因此 `SvgArtworkPreview.vue` 的 sandbox 属性现在是唯一防护，绝不可补上 `allow-same-origin`**（两者同时出现等于完全解除沙箱）。前后端两处代码均写了互相指认的注释。

  仍保留的只有体积上限：它与保真无关，是防止一份几十 MB 的产物拖垮页面与数据库。

- **预览按整页缩放，不直接拉伸**。产物是按桌面视口写的完整网页（常见 900–1200px 宽，多半带 `min-height:100vh` 与固定 `aspect-ratio`），直接塞进几百像素的框里会按框宽铺开、再按自身比例算高度，结果高出容器、下半截被裁掉——表现出来是「画得不对/动画不对」，而产物本身是好的。改为让 iframe 以 900×600 的逻辑尺寸渲染（等于给它一个桌面视口），再整体 `scale` 进容器。
- 评审模型的调用与被检分组走同一个 `intelCheckHTTPClient`（即上一条那个专用 client），复用评审分组自己的 `base_url/api_key/api_mode`；评审提示词中明确"只输出 JSON"，解析失败按 `request_error` 记录而非 `fail`。
- 公开接口挂公共限流中间件。
